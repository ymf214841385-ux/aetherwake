### 1.1 已确认的关键问题

#### A. “点击就是攻击”的入口确实存在

`input.ts` 的 `onMouseDown()` 在排除部分 HTML 界面元素后，将场景左键直接转换为 `attack`，没有先判定是否点中 NPC、宝箱或其他交互对象。键盘 E 则单独生成 `interact`。[^input]

这可以解释鼠标点击物品却挥武器的行为。触屏也可能受兼容鼠标事件、透明触控层及运行版本差异影响，但具体触屏事件链必须录制验证，不能仅凭该段代码断定所有设备上的同一原因。

#### B. 触控按钮的纵向布局存在可计算的溢出

现有八个按钮中，六个最小高度 48 CSS 像素，两个最小高度 56 CSS 像素，按钮间隔 8 像素，整列距离屏幕底部 150 像素。按最小高度计算：

```text
按钮列最小高度 = 6 × 48 + 2 × 56 + 7 × 8 = 456 px
容纳整列所需高度至少 = 456 + 150 = 606 px
390 px 高的横屏视口中，按钮列顶部最多在 390 - 606 = -216 px
```

因此，在这类横屏视口下，上方的“互动、能力、攀爬”等按钮会被挤到屏幕外；这是布局规则推导，不是本次真机截图结论。代码不能因为“DOM 中存在按钮”就被判为合格。[^client][^styles]

#### C. “没有摇杆”不是错觉

`TouchPad` 的左移动区和右视角区是两个空的 `div`，没有摇杆底盘、拇指帽、活动范围或操作说明；样式也没有为这两个区域提供可见的摇杆呈现。[^client][^styles]

#### D. 交互和战斗缺少同帧事务隔离

`Sim.step()` 在调用 `handleInteract()` 后继续执行移动、战斗、能力和敌人更新，没有立即重新检查“交互是否已经进入对话、烹饪或切换世界”。打开地图／行囊的分支也不是全部即时退出本帧玩法处理。[^sim-step]

这会形成同一帧既打开界面又处理其他玩法动作的风险。本次必须修正，不能只修改按钮文字。

#### E. 多处“附近可交互”的口径不一致

`nearInteractable()` 的灵祠范围与 `handleInteract()` 不一致，且两者包含的对象种类不完全一致，例如风之种。该差异可能导致“有提示却走进攀爬分支”或“按键和提示针对不同目标”的体验，必须用同一解析结果取代多套邻近判断。[^sim-near][^sim-interact][^sim-interact-more]

#### F. 操作层可能盖住暂停、对话或横竖屏提示

触控按钮是 `.overlay` 的外部兄弟层，`z-index: 6`；整个 `.overlay` 是 `z-index: 4`。横竖屏提示虽然在内部写了更大的层级，仍处于父层的层叠上下文中。并且 `TouchPad` 不按游戏模式卸载或禁用。应统一层级并增加输入状态门禁，而不是继续提高某个子元素的 `z-index`。[^client][^game][^styles]

### 1.2 人物反向不能先拍脑袋定为“加 180 度”

源码显示，移动方向与 `bodyFwd()` 的 `-Z` 约定基本相互一致，真正需要验证的是正式 GLB 的有效前向、根节点变换，以及动画切换时对根节点的写入。加载器默认使用 `/assets/character/wanderer.glb`，另有只在特定预览配置启用的 v4 资产；修好预览模型不等于修好正式版本。[^sim-direction][^sim-near][^loader]

此外，`animateSkinnedWanderer()` 从原生动画切换到程序化动画时，会遍历记录了 rest 数据的对象并重置其旋转；`Scene.tsx` 又在每帧给角色根节点写入逻辑朝向。这个共享写入边界也需检查，但不能据此断言它就是持续倒着走的唯一原因。[^animation][^scene]

## 2. 修好后，玩家应实际得到什么

### 2.1 移动体验

普通探索时，把摇杆向上推，人物朝镜头所看的前方移动，脸和身体也朝移动方向；左右转向自然，松手后停下。瞄准状态下允许侧移、后退，但必须与普通探索的自动转身规则区分。

### 2.2 交互体验

走近守塔人时看到“交谈”提示和明确按钮，点击后打开对话；走近宝箱时看到“打开”，点击后容器状态和物品栏真实变化。对着物品点一下，不得莫名挥剑。距离不足或条件不满足时，要告诉玩家原因，而不是攻击或静默失败。

### 2.3 任务体验

界面始终能回答三件事：**现在做什么、往哪里走、到了以后怎么操作。** 例如：

```text
当前任务：点亮晨光塔
下一步：沿指引前往塔脚攀爬点
路线距离：按实际计算显示
到达塔脚后：靠近塔壁，点击“攀爬”
到达塔顶后：点击“启动晨光塔”
```

塔脚和塔顶不是同一个任务阶段。不能到达同一 XZ 坐标便显示“已到达”，更不能自动点亮塔。

### 2.4 触控体验

左下角有看得见且随手指运动的摇杆，右侧明确提示可拖动视角，右下角有不超出屏幕的动作按钮。地图、行囊、暂停、能力切换和恢复教程，均能通过触控完成，不依赖键盘。

## 3. 实施边界与总体结构

### 3.1 保留现有基础，不做无关重写

保留现有固定步长模拟、输入队列、多指所有权、碰撞与攀爬／翻越、战斗状态机、存档兼容规则、正式角色模型、地图与场景资产。只在这四类问题必须触及的边界做改造。不得借机更换框架、重写认证／数据库、扩大世界、重新制作全部美术或改成自动寻路代玩。

现有触控已经处理了指针捕获、取消、多指争用及弓按钮的特殊点击激活。这些是需要保留的能力，不是可以用一段简单 `touchstart` 全部替换的负担。[^touch]

### 3.2 推荐的数据流

```text
键盘 / 鼠标 / 触屏 / HTML 按钮
                ↓
输入来源识别 + 指针所有权 + UI / 世界点击分流
                ↓
原有单次指令队列：明确动作、目标 ID、事件身份
                ↓
Sim：当前模式校验 → 目标重验 → 动作执行 → 状态提交
                ↓
业务结果：对话 / 容器 / 背包 / 进度 / 世界状态 / 存档
                ↓
共享只读展示快照
     ├─ 角色与交互表现
     ├─ 任务阶段与当前追踪目标
     ├─ 路线、罗盘、世界标记、地图
     └─ 虚拟按钮文本、可用状态、教程
```

**单一事实来源：** 交互提示和真正执行使用同一个目标解析器；任务完成来自真实进度；画面中的路线与导航计算使用同一个结果；按键可用性来自玩法状态，而不是 UI 自己猜。

### 3.3 默认交互决策

本次默认采用“探索优先、战斗明确”的操作规则：

| 场景 | 输入 | 结果 |
| --- | --- | --- |
| 鼠标未锁定 | 点击可交互对象 | 选择并尝试交互；不触发攻击，不抢占鼠标锁定 |
| 鼠标未锁定 | 点击空白场景 | 获取视角操作焦点；这第一次点击不同时攻击 |
| 鼠标已锁定 | 准星指向明确的非敌对交互对象后左键 | 尝试该交互；不满足条件则解释，不回退为攻击 |
| 鼠标已锁定 | 无交互对象时左键 | 保留攻击／瞄准射击语义 |
| 键盘 | E | 对当前选中的交互对象执行；无目标时才检查合理的攀爬上下文 |
| 触屏 | 点击“互动”按钮 | 只交互，不兼作攻击 |
| 触屏 | 点击“攻击”按钮 | 只攻击／瞄准射击 |
| 触屏 | 短点世界中的对象 | 选择对象；在范围内可直接交互，超出范围提示靠近 |
| 触屏 | 拖动右侧视角区域 | 只旋转镜头；松手不追加攻击或交互 |
| 所有设备 | 点击地图、背包、对话、菜单 | 只处理界面，不向世界下发玩法输入 |

这是本次拟采用的新规则，不是对现有控制表的复述。实现后必须同步标题页、暂停帮助、HUD 和 README，避免保留旧的“任何左键都是攻击”说明。

## 4. 修正一：人物移动和面部朝向

### 4.1 先建立可测量的朝向契约

保留现有逻辑约定：

```ts
// 逻辑朝向：yaw = 0 时面向世界 -Z。
function logicalForward(yaw: number) {
  return { x: -Math.sin(yaw), y: 0, z: -Math.cos(yaw) };
}

function yawFromTravel(dx: number, dz: number): number | null {
  if (!Number.isFinite(dx) || !Number.isFinite(dz)) return null;
  if (Math.hypot(dx, dz) < 1e-5) return null; // 静止时保留原朝向。
  return Math.atan2(-dx, -dz);
}
```

以上是接口意图示例，现有代码已有等价计算，不应复制成第二套相互独立的移动实现。应抽取或复用共同函数，让探索转向、攀爬、攻击、地图方向测试共享约定。

### 4.2 校准正式模型，而不是倒置控制器

在固定光照的检查场景中展示正式 GLB，关闭自动相机旋转，记录正面、背面、左右面，以及以下数据：模型源路径／哈希、父节点变换、根节点初始四元数、逻辑 forward、模型有效前向。

模型“正面”的判定必须来自实际面部、胸部／肩部和脚尖等独立视觉证据；不能把假定的 `-Z` 算一次，再与同一个假定比较，制造一个永远通过的方向测试。

按如下顺序定位：

1. 确认玩家运行的是默认 `wanderer.glb`，还是 v4 候选模型；两个版本分开记录。
2. 不播放动画时，检查模型在逻辑 yaw = 0 时实际面向哪里。
3. 播放 Idle、Walk、Run 时检查有效前向是否变化，是否存在根节点旋转轨道。
4. 从 Walk 切换到 Fall、Bow、Hit、Climb 等状态，检查 rest 恢复或程序化姿态是否覆盖控制器朝向。
5. 对比连续移动的位移方向与模型面向，不只看截图中的一个静态姿势。

**只有测量证明有效前向恰好相反时，才采用绕 Y 轴旋转 π 的资产校准。** 不允许先给 `player.yaw`、镜头或所有骨骼统一加 π。

### 4.3 分离三个变换层

建议在现有加载和渲染代码中建立：

```text
actorRoot                 ← 只由 Sim 的位置与 yaw 驱动
└─ modelBasisRoot          ← 只负责该资产的固定坐标／朝向校准
   └─ authoredRoot         ← 原始 GLB 场景、骨骼、附件及 AnimationMixer
```

实现要求：

- `Scene.tsx` 将世界位置和逻辑 yaw 写到 `actorRoot`，不再直接覆盖参与动画的原始资产根节点。
- `AnimationMixer` 仍以正确的 `authoredRoot` 为绑定根，保持原有轨道目标和骨骼名称。
- `modelBasisRoot` 的校准只在加载或资产切换时设置一次；不得每帧累加旋转。
- 修改 `LimbSet` 等类型时，将世界根与动画根明确区分；原有 `root.userData.mixer/clips/rest` 等数据不能因换层级而失联。
- 容器增加以后，资源释放仍遍历真正资产与运行时附件，不能遗漏几何体、材质或纹理，也不能重复释放共享资源。
- 剑、石板、滑翔伞仍挂在实际骨骼／原有挂点下，不能为了朝向修复破坏手持位置。

当前加载器和动画器的数据归属可以在对应文件中核对。[^loader][^animation]

### 4.4 根运动只能有一个负责人

本次保持“模拟器控制位移，动画表现动作”的方案：Walk／Run 使用原地动画。检查 GLB 轨道时，只移除或转换确实影响角色全局行进／转向的根运动，不要误删骨盆呼吸、步态起伏、攻击躯干旋转。

程序化动画的 rest 恢复只能作用于动画层内部，不得重置 `actorRoot` 和 `modelBasisRoot`。同时增加“动画声明存在但实际 Clip 不存在”的检测；缺失时走明确的回退表现并产生可诊断记录，不能把未播放成功报告成成功。

### 4.5 不同状态的朝向规则

| 状态 | 正确的朝向依据 |
| --- | --- |
| 普通走／跑 | 平滑朝向有效移动方向 |
| 起跳／下落 | 保留合理的行进朝向，允许现有空中转向，不突然转回资产默认方向 |
| 滑翔 | 与实际滑翔转向规则一致，不能视觉倒飞 |
| 攀爬／翻越 | 面向当前攀附面；接近平台、松手和登顶不能错误反转 |
| 持弓瞄准 | 面向瞄准方向；侧移和后退是允许的战术动作 |
| 近战攻击 | 动画朝向与实际判定方向一致 |
| NPC 对话／容器交互 | 停止无关动作，按需要自然转向交互对象，不用攻击动画代替 |

近战目前在命中阶段读取实时相机 yaw，需与角色表现一起回归。建议每次接受攻击时记录攻击朝向，或者明确限制攻击中的转向速度；采用哪种规则都必须同时作用于视觉和命中，不允许镜头瞬间旋转后伤害区域与挥砍方向分离。不要顺便改伤害、耐久和攻击时长。[^sim-near]

### 4.6 朝向验收门槛

以下数值是本次建议的验收阈值，不是已测结果：普通探索稳定行进超过 0.25 秒、速度大于 0.3 世界单位／秒后，模型有效前向与行进方向的水平夹角应不大于 10°。急转身、受击、攀爬及瞄准侧移按各自状态契约验收。

至少覆盖八个输入方向、四个相机方向、走跑切换、起跳落地、攀爬登顶、滑翔、持弓以及读档后第一步。必须保留能同时看清人物正反面与运动方向的录屏，而不是仅提交 yaw 数值。

## 5. 修正二：真实交互，而不是点什么都攻击

### 5.1 从输入源头消除“双重解释”

必须在产生 `attack` 指令之前完成 UI／世界／可交互目标分流。仅给三维物体加 `onClick` 或 `stopPropagation()` 不足以修复现有独立 DOM `mousedown` 监听与其他事件入口；这些入口必须被一起梳理并去重。React Three Fiber 有自己的场景事件分发机制，不能假定它能自动取消另一条已经入队的指令。[^input][^r3f-events]

具体任务：

- 重构 `onMouseDown()` 为可判定上下文的入口，或迁移到统一 Pointer Events 路径；迁移后撤销重复监听，不保留两套同时生成攻击的代码。
- 给每次世界点击附带稳定的激活身份、来源、目标 ID 和世界上下文；一个激活最多生成一种主动作。
- `requestPointerLock()` 只在明确的桌面鼠标视角激活行为中调用，排除触屏、UI、非主键及取消操作；处理拒绝或失败，不产生未处理异常。
- 保留原有固定步长消费模型：一个 DOM 点击不得因一帧运行多个模拟步而产生多次业务动作。
- 禁止使用“只要附近有 NPC 就永远不能攻击”的全局距离开关。明确的攻击按钮仍是攻击；只是点 NPC 的同一次输入不能变成攻击。

### 5.2 处理“透明触控层挡住世界点选”的现实

当前右视角区覆盖在 Canvas 上方。增加物体 `onClick` 后，触屏事件未必会穿过该层到达 Canvas。因此必须有明确的短点桥接：[^client][^styles]

```text
右侧操作区 pointerdown
  → 记录坐标、时间、pointerId、初始目标与所有权
  → 移动超过阈值：判为拖动视角
  → 未超过阈值并正常 pointerup：提交世界短点意图
  → 取消、失去捕获或模式变化：不提交世界短点
```

世界短点由统一拾取服务处理：根据 Canvas 实际 `getBoundingClientRect()` 换算坐标，用同一个相机生成射线；不得使用整屏坐标直接计算，也不得重复乘设备像素比。

建议起始参数为移动阈值 8 CSS 像素、短点时长上限 250 毫秒，随后依真机测试调整。**这些参数属于待验证配置，不是浏览器标准。**

拾取服务只查询受管理的交互对象与必要遮挡几何体。对分组子网格、实例化对象，要将命中结果转换为稳定实体 ID，而不是拿某个临时 mesh 名称直接发奖励。角色自身、纯粒子和不影响交互的特效不应错误阻挡射线；真正墙体和已关闭的门必须阻挡。

### 5.3 建立唯一的交互解析器

新增一个小而明确的交互模块，把以下职责分开：

```ts
// 新接口草案：实现时适配现有 Actions、Sim 和世界对象，不另起一套引擎。
type InteractionPreview = {
  targetId: string;
  worldId: string;
  action: "talk" | "open" | "cook" | "activate" | "enter" |
          "leave" | "collect" | "claim" | "reset";
  label: string;
  enabled: boolean;
  reason?: string;
};

type InteractionExecution =
  | { status: "applied"; targetId: string; modeChanged: boolean; worldChanged: boolean }
  | { status: "rejected"; targetId?: string; reason: string };
```

解析器必须供 HUD、E 键、虚拟互动按钮、世界点击和攀爬后备逻辑共同使用。`nearInteractable()` 应改为该解析结果的派生查询，或者在调用点迁移后删除；不得保留另一套半径和对象列表。

目标选择顺序：**明确点中的有效对象优先 → 玩家已选中的稳定目标 → 视线／距离合适的候选对象 → 无目标。** 同时出现 NPC 和宝箱时，不允许玩家点宝箱，系统却因为遍历顺序先打开 NPC 对话。

预览与执行之间可能发生移动、换场景或目标被收集，因此真正执行前必须再次验证。重复点击用已有集合或专门的一次性状态保证幂等，不能只依赖 UI 上的防抖。

### 5.4 每种对象必须有真实业务结果

| 对象 | 应展示的动作 | 成功结果 | 不满足条件时 |
| --- | --- | --- | --- |
| 守塔人 `SAGE` | 与守塔人交谈 | 打开对话界面；可提供明确的下一目标与追踪入口 | 距离／遮挡不符，提示靠近或绕开障碍 |
| 宝箱 `CHESTS` | 打开容器／具体容器名 | 容器变为已打开；实际背包增加对应奖励；存档记录 | 已打开不重复奖励，显示已搜集 |
| 篝火 `FIRES` | 烹饪／休息 | 打开原有烹饪界面，按原规则恢复与记录检查点 | 条件不符显示原因 |
| 天瞭塔顶部 | 启动某座塔 | `towersOn` 真实增加、点亮表现、存档、推进任务 | 在塔脚不能远程启动；已启动不重复 |
| 灵祠入口 | 进入某座灵祠 | 通过现有 `enterShrine()` 正确进入该世界 | 距离、高差、当前状态不符则解释 |
| 灵祠祭坛 | 领取灵核／离开灵祠 | 通过现有规则领取一次、更新进度并离开 | 不能隔着机关或在入口领取 |
| 灵祠出口 | 离开灵祠 | 恢复合法的原野入口位置和追踪目标 | 不允许串用其他灵祠坐标 |
| 风之种 `WISPS` | 收集风之种 | 增加原有耐力／琥珀奖励；保留既有近距离自动收集规则 | 已收集不重复，不能跨楼层吸取 |
| 掉落物 `pickups` | 自动拾取或明确拾取提示 | 按原规则变更材料、琥珀、生命 | 不因旁边 NPC 提示而停止收集检查 |
| 风桥复位点 | 复位风桥构件 | 仅执行原有构件复位，不抹掉已有进度 | 正常状态不能显示不存在的复位动作 |
| 机关／可施术目标 | 显示对应能力及条件 | 通过实际能力逻辑改变世界，不能用“交互成功”假装解谜 | 未选中能力、冷却或距离不符时解释 |
| 敌人 | 攻击／瞄准 | 继续走战斗逻辑 | 不伪装成友好 NPC 交谈对象 |
| 纯装饰物 | 不显示交互承诺 | 不产生攻击外的虚假业务 | 可短暂标识为装饰；不能写“可打开”却无结果 |

原有奖励、领取集合和自动收集逻辑可在 `handleInteract()` 中核对。本次应复用并拆解它们，不能另写一个只播动画的“假交互”系统。[^sim-interact][^sim-interact-more]

### 5.5 距离、遮挡、高差与状态

以现有交互距离作为回归基线，统一之后再做有记录的手感调整；不要把所有半径直接扩大到几十米来掩盖点不到的问题。

交互校验至少包括：实体存在且属于当前世界、交互锚点、水平距离和合理垂直容差、遮挡、一次性进度、当前玩家状态、冷却、切场景锁。塔顶、祭坛、门口使用真实行动锚点，不使用物体中心或仅用 XZ 距离。

建筑本身的几何体可能包围交互点，遮挡检测要定义允许命中的目标表面与可交互锚点，避免把塔自己的壳体误当成永远不能交互；但不能直接忽略所有同类碰撞体而允许隔墙交互。

没有合法目标时，按钮保留可辨认的外形但禁用，显示“附近没有可交互对象”；点中远处目标时显示“请靠近：对象名称”。被拒绝的交互**到此结束**，不能悄悄回退成挥剑。

### 5.6 自动拾取从人工交互中拆出

`handleInteract()` 当前包含多个提前返回分支，后面的自动掉落物检查可能被前面的对象提示截断。应将自动拾取检查独立到明确的更新阶段，保持现有合法半径，并补齐世界、高差和必要遮挡条件。[^sim-interact-more]

保留风之种近距离自动收集的既有体验；不要为了“统一交互”强行把所有掉落物改成逐个点按钮。人工交互与自动拾取可以在同一帧发生，但不能给同一个对象重复结算。

### 5.7 模式切换成为原子边界

统一提供进入／退出对话、烹饪、暂停、地图、行囊与世界切换的函数：

```text
清除不应跨界面的输入与指针所有权
→ 设置新的模式／世界
→ 按模式暂停玩法或切换输入上下文
→ 释放不需要的指针锁定
→ 同步 HUD 和交互焦点
→ 结束当前不再合法的玩法处理
```

`handleInteract()` 返回“是否改变模式／世界”。发生改变后，本帧不得再使用旧的移动、攻击、能力或目标执行后续玩法；世界切换后的系统从新世界快照开始更新。打开地图或行囊同样处理，不能只有暂停键特殊正确。

退出菜单以后，不应补打一剑、自动跳跃、连续走路或保留弓的旧指针状态。重新进入游戏的第一下点击只做它被定义的动作，不重复充当关闭弹窗、锁鼠标和攻击三件事。

### 5.8 交互表现必须跟业务结果绑定

对话时让人物面向 NPC 并停止无关攻击；打开容器要展示打开或消失后的状态；拾取要显示实际物品和数量；塔激活、灵核领取要看到进度变化。没有专用交互动画时，宁可采用短暂自然站姿、对象状态变化与可靠界面反馈，也不能借用 Attack 动画冒充“开箱”和“交谈”。

## 6. 修正三：任务、目的地与可通行路线

### 6.1 不把“一句话”当作任务系统

目前 `objective()` 按晨光塔、三座塔、四枚灵核、残堡的顺序输出一句文字；地图主要显示塔、祠、残堡点位。没有把当前任务绑定到唯一目标及下一行动，也没有任务路线。[^sim-objective][^ui-map]

本次新增的是围绕现有主线的轻量任务／导航模块，不是大型通用 RPG 任务框架。真实完成状态仍以 `towersOn`、`shrinesOn`、灵核及 `bossDead` 等现有进度为准；封印判断调用现有 `sealIsOpen()`，保留存档中的兼容规则，不能额外写一个只检查数量的 UI 版封印判断。[^sim-save][^sim-objective]

### 6.2 区分四种数据

| 数据 | 含义 | 权威来源 |
| --- | --- | --- |
| 进度 | 已点亮哪些塔、已完成哪些祠、是否击败首领 | 现有 Sim／存档 |
| 任务阶段 | 当前目标需要接近、攀爬、启动、解谜还是领取 | 由进度、世界和位置推导 |
| 追踪选择 | 玩家希望界面优先指向哪个目标 | 玩家选择，或一次性推荐 |
| 路线结果 | 从当前位置到下一行动锚点怎样走 | 导航图与当前通行条件 |

不允许“走到目标附近”直接修改已完成进度，也不允许任务卡上打勾却没有真实获得灵核。

建议的展示模型：

```ts
// 新接口草案；具体实体引用复用当前世界定义。
type WorldRef = "overworld" | "graybox" | `shrine:${string}`;

type TrackedObjective = {
  objectiveId: string;
  targetId: string;
  world: WorldRef;
  phase: "approach" | "climb" | "activate" | "enter" |
         "solve" | "claim" | "leave" | "fight";
  title: string;
  nextAction: string;
  anchorId: string;
};

type RouteResult =
  | { status: "ready"; routeId: string; segments: RouteSegment[]; distance: number }
  | { status: "action-required"; anchorId: string; instruction: string }
  | { status: "unavailable"; reason: string };

// RouteSegment 由导航模块补充完整类型与测试，不把该草案直接当可编译实现。
```

追踪选择要稳定。不能因为玩家走了两步、另一个塔瞬间更近，就每帧更换目的地。只有完成目标、明确切换、目标失效或合理的世界切换时才改变。

### 6.3 主线阶段必须细分到玩家能执行的行动

| 阶段 | 引导内容 | 完成／切换条件 |
| --- | --- | --- |
| 首次进入原野 | 显示控制说明与晨光塔目标；守塔人作为可选教学目标 | 玩家完成对应操作或主动跳过教学，不强制改写主线进度 |
| 前往晨光塔 | 指向经过验证的塔脚接近点，不指向不可站立的塔体中心 | 到达合适接近区域 |
| 攀登晨光塔 | 显示攀爬开始点、平台／休息点、塔顶行动锚点 | 玩家真实攀爬并到达可启动位置 |
| 启动晨光塔 | 显示“启动晨光塔”按钮与对象高亮 | `towersOn` 实际记录 `dawn` |
| 其余天瞭塔 | 在未完成目标中推荐一条可达路线，允许地图自主选择 | 对应塔实际点亮，不能因到达塔脚就完成 |
| 前往灵祠 | 指向该祠入口，显示进入按钮 | 实际调用入口交互并进入正确世界 |
| 灵祠内部 | 切换成当前机关的行动提示，而不是继续指向原野塔 | 世界机关和可通行路径发生真实变化 |
| 领取灵核 | 指向实际祭坛可交互位置 | 领取成功、对应祠进度更新、奖励只发一次 |
| 离开灵祠 | 恢复原野位置、世界地图和合理的后续追踪目标 | 完成实际退出 |
| 前往残堡 | 封印未开时列出缺失条件；已开时指向合法入口路线 | 到达可进入的战斗区域 |
| 挑战空王 | 显示战斗目标，不把普通路线画进不可站立区域 | `bossDead` 真实变为完成 |
| 结局后漫游 | 取消过期主线箭头，允许继续追踪未完成探索目标 | 无重复首领奖励或旧封印阻挡 |

默认推荐顺序可以沿用现有晨光塔起步的设计，但不得阻止玩家先探索灵祠、乱序点塔或中途换目标；读档时按已有真实进度恢复，不要求重新做一遍。

### 6.4 四座灵祠要有各自的内部提示

现有世界定义提供了四种机关及提示，应以此为基础接线，不能用通用“前往目标”掩盖机关操作。[^world]

| 灵祠 | 首要提示 | 路线处理 |
| --- | --- | --- |
| 霜息祠 `rime` | 选择霜息，在指定水面形成可踏的霜柱 | 未形成可行路径时先引到施术区域，不直接画穿水／坑的步行线；冰体失效后重新判定 |
| 爆鸣祠 `burst` | 选择爆鸣，处理裂纹岩壁 | 墙未破时终点是施术位置；破坏与碰撞更新后才显示后续通路 |
| 牵引祠 `pull` | 选择牵引，移动金属板形成通路 | 使用真实板体位置和支撑条件；不能因板子“看起来接近”就判为已搭桥 |
| 凝时祠 `still` | 冻结移动石块，并在有效窗口通过 | 路线需反映动态石块和冻结时限；不能把不存在的旁路画成常驻通道 |

基础任务提示可以保持简短；玩家停滞或主动点击“任务帮助”时再提供更明确的提示。提示不会代为施术、生成桥、冻结石块或发放灵核。

### 6.5 路线实现：采用关卡路径图，不先引入重型重构

针对现有固定世界，优先采用“**人工确认的关键节点／连接图 + A* 或同等最短路径搜索 + 局部可通行连接验证**”。这是本次建议的实现取舍，目的在于可控修复，而不是声称仓库已有导航系统。

导航数据必须覆盖所有主线塔、四祠入口、残堡合法入口，以及灵祠内部必要行动点；只完成出生点到晨光塔的一小段不算完成“完整修正”。

每个节点至少包含：稳定 ID、所属世界、锚点位置或实体引用、用途。每条边至少包含：起终点、移动方式、条件、代价，以及验证依据。

移动方式区分：步行、攀爬、滑翔、游泳、机关行动、世界入口／出口。特殊边不能统一渲染成“地面直接走过去”的线。

**节点和边的约束：**

- 目标优先引用 `world.ts` 的实体和已有实际坐标。该文件中的部分高度会在世界初始化时确定，不能直接复制初始化前的 `y: 0` 作为路线高度。
- 塔顶、平台、桥和灵祠内部要使用对应的真实支撑面；不能一律使用原野 `heightAt()`。
- 普通步行连接必须考虑玩家体积、碰撞和坡面，不能只验证一条没有宽度的射线。
- 攀爬路线节点应对应真实可攀附面和可站平台，不能绕开现有耐力与翻越约束。
- 冰柱、金属板、风桥、冻结移动物等动态通路，用实际世界状态控制边的可用性，并在失效时更新。
- 穿越灵祠入口属于世界切换，不在同一原野坐标图里画一条跨世界长线。
- 导航只指导玩家，不直接写玩家坐标、不代按互动、不改变障碍物或奖励状态。

### 6.6 不能以“画一条直线”冒充路线

地面路线只绘制已经确认可通行的步行部分，沿实际支撑面布置，并保持略高于表面的可读偏移。碰到墙体、悬崖、深坑、关闭的门和未完成机关时必须停止或切换为相应动作提示。

确实没有可行路线时，显示具体原因，例如“需先搭建通路”“当前路径被机关阻挡”“尚未找到可达路线”。可以额外保留一个明确标为“目标方向”的远方标记，但不得把它标成可步行路线。

距离同样分开：有实际路线时显示路线长度；只有空间定位时写“直线距离”。塔脚到塔顶的引导要提示垂直任务，不得以 XZ 距离为 0 误报完成。

### 6.7 五层指引要使用同一个追踪结果

| 层级 | 呈现内容 | 关键要求 |
| --- | --- | --- |
| 任务卡 | 当前任务、下一行动、距离／缺失条件 | 不只写“收集 4 个”，而要说明当前追踪哪一个 |
| 罗盘／屏幕边缘箭头 | 目标在镜头左右、身后及大致方位 | 处理镜头背面和屏幕外目标，不能镜像反转 |
| 世界目标标记 | 当前目标的名称、行动位置、高差提示 | 不给所有目标同时放同样醒目的标记 |
| 地面路径／动作节点 | 可走路段、攀爬入口、施术位置 | 不是穿墙、穿坑直线，不替玩家完成操作 |
| 大地图／小地图 | 当前选择、已完成状态、路线和切换入口 | 点击图标可以追踪；触屏不依赖鼠标悬停 title |

到达最后行动范围后，远方引导应让位于交互提示，例如“已到塔顶：启动晨光塔”，而不是一直显示“前往晨光塔”。地图方位、小地图玩家箭头、角色逻辑 yaw 和罗盘相对方位必须一起测试，避免修好角色以后地图又反向。

### 6.8 重算、性能与世界切换

初始建议：在目标改变、世界切换、通路状态改变或偏离当前路径约 4 个世界单位时重算；连续偏离检查可节流到约每 0.5 秒。数值属于待调参数，不是强制照抄的业务规则。

路径计算与 DOM 更新不得每帧全量运行。路线几何在结果变化时更新，角色朝向和标记投影可以走现有帧循环；HUD 用选择器或适当频率发布轻量快照，避免为每个拖动像素重渲染整棵 React 树。

切入灵祠、离开灵祠、死亡复活、读档、完成当前目标后，必须清除上一世界的路线和旧实体引用，然后重新解析当前任务。路径不可达时不得输出 NaN、无限距离或一个伪造的 0 米成功状态。

### 6.9 旧存档兼容

追踪目标和教程记录是可选扩展，不得让旧档因为缺少新增字段而无法读取。执行者需审查 `persistence.ts` 的校验、默认值和版本迁移，决定是扩展原存档还是使用独立且可校验的 UX 设置；无论采用哪种方式，都不能默默清空原有档。[^sim-save][^readme]

加载后校验目标 ID：已完成、未知或属于错误世界的目标应重新选择或给出提示；已完成的塔、祠、容器不能再次发奖。自动保存失败要明确告知“当前进度仍在内存”，不重复发放奖励，也不能把“未写入磁盘”显示成已保存。

## 7. 修正四：可见、可用、可理解的虚拟操作

### 7.1 目标布局

采用左移动、右视角、右下紧凑动作区、上方轻量菜单的横屏布局。以下是布局意图，不是像素稿：

```text
┌──────────────────────────────────────────────────────────────┐
│ 生命 / 状态              当前任务与方位       地图 行囊 暂停 帮助 │
│                                                              │
│                       游戏观察区域                            │
│                                                              │
│ 左侧移动区                            右侧空白区拖动视角       │
│   可见摇杆             对象名称 / 下一步           [互动]      │
│    ◉                                         [能力] [跳/翔]   │
│  移动 / 外圈冲刺                              [闪避] [攻击]    │
│                                               [弓/瞄准]       │
└────────────────────── 设备安全区 ──────────────────────────────┘
```

按钮位置应按实际可用高度调整为两列或紧凑弧形；不再采用“八个按钮整列向上堆”的方案。地图／行囊／暂停移到轻量菜单区，不挤占主要拇指操作区。

### 7.2 摇杆必须看得见，也必须跟手

建议初始规格：底盘直径约 120–136 CSS 像素，拇指帽约 44–52 像素，逻辑行程继续使用现有 54 像素尺度或等价归一化配置。规格应通过小屏与平板测试后确定。

应具备：常驻的低干扰底盘、按下高亮、与输入值对应的拇指帽偏移、松手归中、死区反馈、外圈冲刺提示。显示层与真正命中范围要一致，不能画在左下角却仍由半屏任意透明区域产生难以预测的移动。

默认建议固定位置摇杆；如保留浮动起点，也要显示该次手势实际起点和范围，不能完全隐形。菜单、地图、任务卡区域不能被移动手势占用。

### 7.3 按钮应随上下文说明动作

| 按钮 | 显示规则 | 不允许出现的情况 |
| --- | --- | --- |
| 互动 | 交谈、打开、启动、进入、领取、离开等具体动作 | 点一下实际触发攻击；显示“领取”却没有可领取对象 |
| 攻击 | 普通攻击；瞄准时可明确显示射击 | 被互动按钮复用且无法区分 |
| 跳跃 | 地面“跳跃”；满足滑翔条件时显示“滑翔” | 任何时候都写“跳／翔”却不说明不可用原因 |
| 闪避／松手 | 地面闪避；攀爬时松手；按当前状态启用 | 静态文字与真正动作不同 |
| 攀爬 | 仅有合法攀爬上下文时提供；可并入交互上下文 | 对着 NPC 按互动却被攀爬抢走 |
| 能力 | 显示当前能力；提供触控可用的五术选择入口 | 手机只能施放第一种能力，切换还要按键盘 1–5 |
| 弓／瞄准 | 明确开关状态，沿用可靠的单次切换规则 | 一次点击因多个事件翻转两次 |
| 地图／行囊／暂停 | 可被触屏直接打开和关闭 | 必须按 M、Tab、Esc 才能进入或退出 |

主要动作建议 56–64 CSS 像素左右，必要点击目标不小于 48 像素，间距建议 8–12 像素。较小的视觉图标可以有更大透明命中边距，但相邻可点击区域不得重叠。所有尺寸属于本次设计起点，以实际可用性验收为准。

### 7.4 不以屏幕宽度推断“是不是手机”

现有显示规则是 `(pointer: coarse)` 或宽度不超过 800 像素；它不能覆盖所有大屏触控和混合输入情况。应新增设置：**自动、始终显示、隐藏虚拟操作**。[^styles]

自动模式综合触控能力、可用指针类型及最近发生的真实触摸事件，不依赖 User-Agent 字符串。`any-pointer` 可以用于检查设备可用的指针类型，但它也不是用户此刻输入意图的完整替代。[^any-pointer]

关键要求：检测失败时仍能从开始页和暂停设置一键打开虚拟操作；触控设备接入键盘或触控板后，不能突然移除玩家正在使用的摇杆。键鼠用户保留常驻可查询的操作提示，不显示触屏 UI 也必须知道按什么。

### 7.5 统一层级和输入门禁

将各层放到统一的顶层容器，给它们明确的层级语义，例如：

```text
世界画面 0
任务 / 路线提示 10
正常游戏操作 20
菜单 / 对话 / 暂停 40
横屏提示 / 致命错误提示 50
```

以上是拟采用的层级方案，不是现有值。重要的是处于可比较的层叠上下文，而不是仅把子元素数值加大。

游戏操作只在正确的玩法模式中启用。暂停、对话、烹饪、行囊、地图、死亡、标题、结局和竖屏暂停期间，移动与战斗输入要从处理层禁用，必要时隐藏；对应界面使用自己的确认和关闭按钮。即使某个浏览器层级渲染异常，也不能导致背后的角色继续行动。

### 7.6 安全区、视口与横竖屏

布局以当前实际可视区域为准，考虑浏览器工具栏、横屏刘海、圆角和底部系统手势区域。使用安全区变量和经过验证的视口高度方案，必要时订阅可视视口变化；不要写死“底部 150px”。

竖屏时沿用安全暂停／横屏提示的产品方向：先释放输入，再显示提示；转回横屏后重新计算布局，不能出现粘住的移动或攻击。桌面窗口变窄、平板分屏也要有可理解的提示，避免不说明原因就冻结。

任务卡、拾取提示、能力选择和小地图必须一起参与布局，不能只让按钮彼此不重叠，却让提示文字盖在攻击按钮下面。横屏高度不足时缩减次要常驻 UI，将能力列表和详细状态收进菜单，不能缩小核心按钮到不可点。

### 7.7 保留并扩展可靠的多指控制

沿用 `bindTouchInput()` 已有的指针所有权与重置订阅，展示层从真实状态读取摇杆／按钮状态，不重新建立一套与输入脱节的数据。Pointer Events 的捕获与取消机制可用于让手指离开按钮边界后仍正确结束手势。[^touch][^pointer-events]

必须支持左手移动、右手转镜头、第三指按动作，并满足以下行为：

- 每根手指只拥有一个控制区域；第二根手指不能悄悄抢走已经按住的摇杆。
- 手指滑过别的按钮不等于按下别的按钮；松开其中一指不能清空其他仍有效的手指。
- `pointerup`、`pointercancel`、`lostpointercapture`、窗口失焦、切后台、转屏和组件卸载都能结束对应状态。
- 切换模式时清空所有玩法输入；回到游戏后等待新的真实按下。
- 不把 `pointerdown`、兼容鼠标事件和 `click` 各当作一次独立操作。
- 保留弓按钮对真实指针释放、键盘激活和辅助技术点击的处理；不能为了防重复把所有无指针的合法按钮点击一刀切禁掉。
- DOM 焦点位于输入框、菜单和可访问控件时，键盘空格／回车不能顺带触发世界跳跃或攻击。

### 7.8 触控合格不等于按钮“存在”

自动化和人工验收都必须检查：实际 computed style、可见面积、边界矩形是否在安全可视区内，以及按钮中心和边缘的命中对象。使用 `elementFromPoint()` 检查遮挡只能作为辅助，仍需发送真实的点击／拖动并观察玩法结果。

## 8. 新手引导：不再让玩家猜半屏哪里能按

新增可跳过、可重播的轻量教学，不强制长篇弹窗：

| 教学阶段 | 玩家看到的内容 | 真正完成条件 |
| --- | --- | --- |
| 移动 | 高亮可见摇杆，提示“拖动移动，外圈冲刺” | 玩家实际产生有效移动 |
| 看方向 | 高亮右侧视角区域，提示拖动观察 | 玩家实际改变镜头角度 |
| 跳跃／滑翔 | 高亮对应按钮，结合当前环境说明 | 在允许状态下真实完成相应动作 |
| 首次交互 | 对守塔人或初始容器显示名称和交互按钮 | 对话打开或容器奖励真实到账 |
| 开始追踪 | 高亮任务卡和地图追踪入口 | 玩家理解当前目标；追踪状态实际存在 |
| 攀爬／能力 | 在塔脚或机关前显示对应上下文 | 真正进入相应动作或产生有效机关变化 |

教学按玩家完成的动作推进，不按时间自动标成已学会；已会操作的玩家可跳过，暂停帮助可重新观看。没有键盘的玩家不能看到“按 E”作为唯一说明，有键盘的玩家也不能只看到不知对应何键的触控图标。

守塔人对话可以在原有世界观说明基础上增加“追踪晨光塔”“查看操作说明”两个明确入口；它们只切换指引和界面，不直接给塔或灵核进度。

## 10. 分阶段执行计划

没有通过阶段出口，不得在报告里把对应问题标为“已修复”。阶段划分是执行依赖，不是工时承诺。

### M0：锁定玩家版本、建立失败证据

**执行：** 读取仓库实际当前状态，记录源码 SHA、运行地址、构建标识、模型 URL／哈希、视口和输入模式。若执行时 HEAD 已前进，重新核对相关变更，不对旧行号机械打补丁。

正常启动新档和一份旧档，复现四项症状，记录点击事件顺序、模式变化、逻辑与模型方向、按钮边界、当前目标。不能为了做复现录屏直接修改玩家坐标或奖励。

**交付：** 基线复现表、屏幕录制／截图、失败测试、部署版本核对结果。无法复现的项目保留为“待定位”，不擅自删掉用户反馈。

**出口：** 清楚区分已复现缺陷、静态确认缺陷、部署差异与模型待测项。

### M1：先让操作可见，并修正输入分流

## 13. 最终完成标准与禁止的“假修复”

### 13.1 完成标准

- [ ] 正式发版模型普通走跑时面向行进方向，动画状态切换和读档不破坏该结果。
- [ ] 点击 NPC、容器与其他交互对象产生正确的实际行为，同一次输入没有额外攻击。
- [ ] 交互提示、选中目标、可用范围和实际执行使用统一结果；失败能解释。
- [ ] 已完成对象不重复发奖，自动拾取不被人工交互分支吞掉。
- [ ] 新档、旧档、乱序主线和灵祠内部都能看到正确的下一行动和追踪目标。
- [ ] 路线覆盖全部主线目标，区分地面、攀爬、机关和跨世界；不会画出假通路。
- [ ] 摇杆与动作按钮可见、跟手、实际可点，手机横屏不溢出、不被弹窗遮挡。
- [ ] 地图、行囊、暂停、五术选择和教程都能纯触控使用。
- [ ] 多指、取消、失焦、转屏、切后台与菜单往返不会产生粘键或补发动作。
- [ ] 保留原有碰撞、攀爬、战斗、存档与封印规则的正确性，没有以削弱规则换取通关。
- [ ] 50 项用例有真实执行记录；缺设备或未完成项没有被填写为通过。
- [ ] 应用构建、发行包、部署版本和正式资产对应，正常输入录屏可追溯。

### 13.2 下列情况不能算修好

| 看起来像修复 | 实际为什么不合格 |
| --- | --- |
| 把 W 和 S 对调 | 人物模型问题被挪到了移动控制与镜头关系上 |
| 给所有骨骼或全局 yaw 加 180° | 可能破坏骨骼动画、攀爬、武器和命中；没有完成资产校准 |
| 只修 v4 预览模型 | 默认发版 `wanderer.glb` 仍可能错误 |
| 点 NPC 先挥剑再弹对话 | 输入没有隔离，原始问题仍存在 |
| 所有交互都播放同一攻击动画 | 没有真实交互表现；可能连业务状态都没改变 |
| 把半径扩大到很远 | 用远程触发掩盖目标识别、遮挡和命中问题 |
| 在地图上画出生点到目标的直线 | 不等于玩家能走的路线，塔顶、机关和墙体仍然无法解释 |
| 到了塔脚自动点亮塔 | 绕过玩法，破坏原有进度规则 |
| DOM 查询能找到互动按钮 | 不能证明按钮在屏幕里、未被遮挡、真正可点击 |
| 单元测试通过就宣布手机通过 | 没有验证真实浏览器事件、CSS 布局与多指体验 |
| 控制台传送到目标、直接设定进度 | 不能证明正常玩家能依照操作和指引完成游戏 |
| 清空全部旧存档解决报错 | 破坏玩家数据，不是兼容修复 |
