## 1. 项目目标与不做事项

### 1.1 最终体验

把《风醒》从“有许多冒险功能的程序原型”，改造成一个角色可信、控制可靠、空间有层次、探索有回报的原创风格化第三人称冒险游戏。

体验主线：

> 看见值得去的地方 → 自己选择路线 → 攀登并观察 → 借风滑翔 → 在场景里尝试解决问题 → 获得奖励或捷径 → 看见下一个目标。

借鉴《旷野之息》的开放探索气质，而不是复制其角色、地图、界面、音乐和资源。以下关卡节奏、参数、风机制及视觉方案均为本项目设计建议，不是原作官方规格。

### 1.2 三项不可互相替代的质量

**操作质量：** 走、跑、跳、攀、滑、转镜头和攻击必须有明确规则；玩家的失误与程序错误可以区分。

**画面质量：** 主角、动画、地形轮廓、光照、草木、水和遗迹属于同一套美术；不能仅改天空颜色和加泛光。

**游玩质量：** 地点之间有看得见的关系，玩家有选择，机关有因果，奖励能改变后续行动，而不是不停走到图标按互动。

### 1.3 范围控制

沿用网页 3D 与现有 React / React Three Fiber / Three.js 技术路线。电脑键鼠和手机横屏触控都需要完成主线；竖屏至少提供清晰的转横屏提示和安全的暂停/继续，不把竖屏玩法作为第一轮核心设计。

保留能用的固定步长、实例化、对象池、项目路由和现有基础设施。允许有边界地重构游戏核心，不做无关后端重写或全套框架升级。

本计划不增加大陆规模地图、联机、商城、账号体系、复杂生态模拟、骑马、全动态火电冰化学系统或十几种新敌人。不改成 Unity、Unreal 或 Godot 项目，不重新立一个不能接续当前仓库的游戏。

### 1.4 既有内容的处理原则

基线 `world.ts` 列出三座塔、四个灵祠、三个营地、八个风之种，以及残堡等地点。[R5] 执行时先按实际 HEAD 清点。

先在代表性区域集中精修，未改造区域临时保留为旧版入口/开发开关，不立即删除。M8 要把本轮需要保留的既有内容逐项接到新基础系统并验证完整流程。不能通过隐藏全部旧内容，声称已经完成全图改造。

既有四术暂时保留接口和旧档语义。代表性区域只重点呈现“引风”这一新增核心能力；到 M8 再逐项整合既有四术，避免同时重做五套能力。任何删减必须列出影响，不能悄悄把删功能当修复。

## 5. M1：优先修复 P0 与存档

### 5.1 输入系统

将输入拆成三类：持续状态（方向、按住）、带序号/时间的一次性命令（跳、攻击、交互、菜单、能力切换），以及视角增量。

设备采集与模拟消费分开。没有模拟步时，事件留在队列；有多个模拟步时，同一事件只能被消费一次。视角增量只应用一次，不能在每个补帧重复使用；如选择在渲染层更新镜头，也必须保证模拟方向与镜头使用同一权威状态。

键盘与触控分别计算方向和冲刺意图，最后再统一归一化。键盘 W 不能因为幅度为 1 自动冲刺；触控外圈冲刺只判断对应摇杆本身。

统一 `resetInput()`：失焦、页面隐藏、暂停、死亡、新开局、切场景、触摸取消、指针捕获丢失都要有明确策略。清理按住状态、边沿命令、触摸、视角增量和弓箭过渡状态；恢复后不执行失焦前排队的攻击。

在 30/60/90/120/144 Hz 和随机帧间隔下测试至少 100 次有效短按。一次性输入不得丢失、不得重复。冷却期间的攻击丢弃/缓冲要有明确规则，测试不得把设计拒绝和设备丢失混为一谈。

### 5.2 碰撞的最小可信修复

支撑查询排除自身，并区分脚下支撑、身体侧面障碍、头顶障碍。物体位于同一 x/z，不代表其顶面就是可站立地面。

取消“向上跳就允许水平进入任何高度障碍”的放行条件。落地吸附只能作用于脚底附近、方向正确的可站立支撑，不允许把地面角色传送到塔顶。

采用与后续统一碰撞层兼容的补丁和回归用例，避免为了立即修复而再建立一套无法整合的物理系统。

### 5.3 存档必须先保护再改

把“创建默认运行状态”与“写入新游戏存档”分离。`continueSave()` 不得先运行会覆盖旧档的初始化。

新增有版本与世界标识的存档封装：`schemaVersion`、`worldVersion`、`savedAt`、`player`、`inventory`、`progress`、`checkpoint`。不要直接反序列化任意数据进入运行时。

解析后做类型、有限数值、范围和必需字段校验。用按字段定义的默认值处理缺失，不用 `Number(x) || 默认值` 统一处理；合法的 0 必须保留，非法 0 是否允许取决于字段。

新精修区域默认使用独立存档键，保留 `aetherwake-save-v1` 原文；迁移前先做备份。坐标随地形变更失效时，按持久检查点 ID 恢复到新世界的安全地面，不盲目使用旧 y 值。

损坏存档、写入空间不足或权限失败时，提示并保留可恢复数据，不偷偷清空。普通状态修改采用受控自动保存，避免每帧写 localStorage；进入检查点、领奖、重要进度变化时保存，后台隐藏只做尽力保存，不依赖关闭页面时才保存。

装备和道具用稳定 ID 引用。删除武器后重新校验装备和弓的引用。重生、新开局、进入灵祠、离开灵祠都要集中清理临时状态；从塔顶检查点重生不能落入塔体内部。

### 5.4 M1 验收

至少覆盖：普通行走不扣冲刺耐力；斜向不加速；短按事件一次消费；60 秒物体稳定；跳墙不吸顶；后台返回不粘键；UI 点击不攻击；0 坐标和 0 箭数读档正确；损坏档不覆盖原文；读取旧档再立即退出不会把旧进度改成新游戏；武器损坏后弓和近战仍有合法状态。

## 6. M2：统一模拟、运动与镜头

### 6.1 技术路线与权威状态

推荐先在灰盒中验证 Rapier 运动学胶囊角色控制器，用它处理移动与基本碰撞，再在其上实现游戏特定的攀爬、滑翔、耐力和战斗状态。Rapier 官方明确提供运动学角色控制与形状检测能力，但并不保证开箱即用适合所有玩法，攀爬和滑翔仍需本项目实现。[D1]

这不是要求盲目引入依赖：先检查实际 Three/R3F 版本、WASM 加载、包体和构建兼容性。当前没有必须使用某个 React 封装的要求。若有已验证的现有统一碰撞方案，可保留，但必须通过同一组测试，并在决策日志说明理由。不要让两套碰撞方案长期各自改变角色位置。

角色与可搬物体的位置、速度、碰撞结果只有一个权威来源。渲染层插值和播放动画，不回写第二套移动公式。物理世界由一个固定时钟推进，不允许模拟器和渲染组件各 step 一遍。

固定步长基准为 1/60 秒。限制单帧补步数并记录超限；切后台采用暂停与清空累积器策略，恢复不追赶几分钟的历史模拟。不能为了提高帧率偷偷改变游戏速度。

### 6.2 状态机

运动状态至少有 `Grounded / Airborne / Climbing / Gliding / Swimming / Dead`，同一时刻只有一个主运动状态。战斗、受击、交互作为受约束的动作状态，不再依赖可以任意同时为真的多个布尔值。

每个状态明确进入条件、保持条件、退出条件、重置项和输入消费。水面、攀爬、滑翔和死亡转换不能留下旧重力、旧速度或无效动画。

### 6.3 可试玩的移动参数

先统一 1 世界单位约等于 1 米、角色高度约 1.7—1.85 米的测试尺度。下表只是初始调参范围，不是必须机械照抄的数值，也不是原作参数。

| 参数 | 建议起点 | 关注点 |
|---|---|---|
| 普通移动 | 3.8—4.8 米/秒 | 清楚区分走与冲刺 |
| 冲刺 | 6.5—8.0 米/秒 | 不靠夸张相机变化冒充速度 |
| 起步加速 | 0.12—0.25 秒到主要速度 | 有响应但不瞬间滑移 |
| 制动 | 0.10—0.20 秒量级 | 松手后不长距离漂移 |
| 跳跃输入缓冲 | 100—150 毫秒 | 落地前短按可接续一次跳跃 |
| 离边容错 | 80—120 毫秒 | 刚离平台可完成预期起跳 |
| 镜头垂直 FOV | 约 50—60 度起调 | 根据设备画幅整体校准 |
| 镜头距离 | 约 5—7 米起调 | 与角色屏幕占比、障碍一起测试 |

参数集中管理；调整一项后重跑移动距离、跳跃高度、攀爬消耗和滑翔落点测试。渲染刷新率变化不能让移动速度变化。

### 6.4 攀爬与滑翔

攀爬以身体前方接触面、可攀标记、接触法线和边缘条件判断；不是以镜头朝向判定墙。沿墙切线移动，攀到顶缘前检查头顶和落脚空间。加入休息平台、耗尽耐力后的可理解脱离、主动松手与安全恢复。第一段教学攀爬应留足耐力余量。

滑翔必须有展开、持续和收起过程。地面起跳、空中再次按跳跃切换滑翔；不要强制手机长按才能维持整段滑翔。速度、下沉、转弯与风场共同决定落点，镜头不能硬拽方向。着地、入水、受击、耐力耗尽都有确定出口。

首版不要求严格空气动力学，但禁止“任何方向都像水平飞行”“轻推摇杆就突然掉落”“镜头朝向改变立即横向瞬移”。

### 6.5 相机

用目标点到理想镜头之间的球扫/等效体积检测防遮挡，处理近裁剪面，不只做一条终点高度检查。靠墙优先拉近，离开后平滑恢复，避免突然抬高和跳远。

探索、攀爬、滑翔、瞄准使用不同配置，共用同一相机管理器。合理允许抬头看高塔与山顶；进入菜单释放指针锁，返回后通过合法用户交互重新获得，不自动抢鼠标。

观察移动与攻击使用同一坐标约定，明确模型前向、角色 yaw、镜头 forward/right。验收正前、正后、左右移动与转镜头后攻击，防止角色倒着跑或向另一边出刀。

### 6.6 M2 验收

在灰盒连续操作至少两分钟，覆盖走跑跳、平台边缘、斜坡、台阶、头顶、窄道、贴墙转向、攀爬、顶缘、滑翔和落水。不同刷新率结果在设定容差内；相机不持续穿墙、人物不被墙挡住、身体不抖、不瞬移。

## 7. M3：地形尺度与首个精修区域

### 7.1 地形不再只靠噪声

保留现有地图量级，不扩大外边界。先由人工可控数据定义主山脊、台地、谷底、水域、崖面、道路、地标和留白，再用噪声添加次级起伏。

海岸衰减不能把整个目标山体乘平。高度图可用于地表；需要洞口、悬挑、桥下空间的地方，用真实网格和匹配碰撞体补充，不能期待单值高度图表达上下两层。

统一视觉与碰撞数据源。三角地形的地面高度应匹配实际三角面，不把另一个解析函数或不同插值结果当作精确碰撞；近景脚底与石块接地尤其需要检查。

### 7.2 推荐空间关系

先制作一个原创“风谷”代表性区域：出生点附近有遮挡的小路，走出后能看见远处风塔；中途有短崖和休息平台；高处有可选择的滑翔落点；落点附近有遗迹、浅水和可绕行营地；完成机关后打开回程捷径。

目标是至少两条可行路线，不是把单一路径做得更长。主目标可以被地形短暂遮挡，过山脊后重新出现，形成发现感。道路、树线和光照引导玩家，而不是满屏箭头。

初始角色可完成关键路线。塔高、平台间距、耐力消耗、起跳高度、滑翔距离在同一测试表里验证。高塔需要休息平台或侧路，不能只有模型上的装饰圈。

寒冷判定改为区域气候与高度等可解释因素的组合。温暖地区登一座塔不应只因为超过固定 y 值突然变成雪山气候。

### 7.3 道路与地标布置

每个重要地点都有远看可识别的轮廓与近看可理解的入口。禁止全图平均撒树、撒石头；分区控制植被密度，保留玩家落点、战斗空间和关键视线。

可交互物体、敌营与机关不能出生在水底、斜坡边缘或碰撞体内部，除非该位置本身是明确设计且通过测试。按地形法线、净空、可达性与场景语义验证落点。

### 7.4 M3 验收

关闭任务箭头后，仍能从起点看懂至少一个主要目标与一个可选目标。按正常操作完成两条路线与第一段攀滑；没有强制传送、坐标判定绕过或穿模捷径。输出路线示意、地标清单和攀滑参数验证结果。

## 8. M4：主角、动作与角色呈现

### 8.1 主角的完成标准

接入一名完整的原创或授权可用风格化角色。轮廓、比例、服装层次和装备都要清晰；头、手、肘、膝、脚具有合理结构。不要把现有球头圆柱人换一种颜色，就称为人物重制。

推荐角色方向：轻装旅行者，身形利落，短披肩或轻围巾、实用腰包、可识别的滑翔装备；自然低饱和底色加小面积暖色识别点。服装、发型、配饰和标记必须保持原创，不做林克的换色版本。

素材形态优先为可本地加载的 GLB/glTF、统一单位和轴向、完整骨骼与动画。材质、贴图和动画的授权都要核对，不只有模型本体的授权。禁止在运行时依赖不稳定第三方热链。

资源预算先以桌面和移动共用为目标：一个主要骨骼角色、少量材质、必要纹理和至少一个低细节版本。多边形和纹理预算由 M0 实测能力确定，不能用“面数更多”作为角色质量验收。

### 8.2 素材无法获得时如何执行

先检查项目现有资源。没有合适资源时，在实际可用工具范围内获取明确授权的资源，或制作真正具有完整造型与骨骼的原创资源；不得假装已经调用了并不存在的建模工具。

临时占位模型可以用于控制器和测试，但必须标记 `placeholder`。建立 `ASSET_GAPS.md`，列出缺少的资源、预期格式、骨骼/动画要求、授权要求和受阻验收项。继续可独立完成的工作，不得据此宣称最终美术已经完成，也不擅自付费购买。

### 8.3 必备动画与衔接

第一轮必须完成待机、普通移动、冲刺、起跳、下落、落地、攀爬、顶缘翻越、滑翔展开/保持/收起、轻攻击、受击、死亡；保留弓与水中路线时，同时完成基本瞄准/射击与游泳动作。

动画由实际状态和速度驱动，有合理混合与过渡。每次进入状态统一恢复受影响姿态，防止上个状态留下手臂或武器旋转。脚步相位与地面速度匹配，起跳和落地不是继续播放走路循环。

本轮默认采用控制器驱动位置、原地动画跟随速度的方案，不让根运动与物理控制双重位移。必要的坡面脚部适配可逐步加入，但不把复杂 IK 当作基础动作完成的前提。

武器、弓和滑翔装备挂在稳定骨骼/挂点上。命中窗口由动画事件或统一动作时间表驱动；禁止动画在挥剑，伤害却早已在按键那一刻结算。

### 8.4 M4 验收

近距离正面、侧面、背面以及正常游戏距离都检查角色。连续执行走→跑→跳→滑翔→落地→攻击→受击，动作衔接合理，无持续脚滑、倒着跑、武器悬空和大面积穿身。

提供实际运行中的主角近景、运动片段和资产授权记录。渲染出的静态角色宣传图不能替代游戏内动作验收。

## 9. M5：统一视觉系统，而不是单个滤镜

### 9.1 美术定义

整体方向：明亮、轻盈、有风感的手绘野外冒险。草地以自然暖绿为主，水与空气偏青蓝，远山偏灰蓝，岩石和遗迹偏暖灰；交互能量只占小面积强调色。具体配色由实机调整并集中管理。

必须同时成立的画面关系：近景有可触及的草、石和角色；中景有可到达的路线、遗迹和林地；远景有独特地标；最远山体与天空形成清楚轮廓。不要用厚雾把缺少的中远景全部遮住。

先锁定一个白天光照预设，做出质量基准，再恢复其他时间与天气。不能让过快的昼夜循环破坏画面验收，也不能用夕阳滤镜掩盖白天效果。

### 9.2 光照、材质与后期

建立角色、草木、地形、岩石、建筑、水六类统一材质约定。可以使用温和的明暗分层和手绘色块，但不是给所有物体套同一个平涂材质。角色需要在背景中可读，阴影中也保留细节。

校准主光、环境补光、接触阴影、阴影偏移与阴影覆盖范围；不允许大片漏光、阴影痤疮或角色明显悬空。统一颜色空间、色调映射和曝光，避免重复转换导致灰白或过曝。

先做基础光照，再决定是否加少量后期效果。强泛光、厚黑描边、过饱和草地、模糊滤镜不能作为“像目标风格”的捷径。默认不引入昂贵的全屏效果堆叠。

### 9.3 地表、草木与天空

地表区分草、土路、岩面、湿地和岸边，过渡与坡度/路径一致。岩石造型要有大中小尺度，不是反复缩放同一个几何球；道路上留下可行走净空，重要台阶和崖缘形状清楚。

近景草按簇和密度分布，远处逐级简化。树干、树冠有形态变化；草与树冠共享风场方向，但有相位、刚度和幅度差异。不要每株草都建立独立的逐帧 React 状态更新。重复资源继续采用实例化、复用和必要的分区，这与 R3F 官方性能建议一致。[D2]

天空有清晰的天顶与地平线色彩关系，云层轻微移动，远山有空气透视。天空、雾、太阳方向和场景时间使用同一套环境状态，进入灵祠时不因为旧坐标偏移导致天空或地面错误穿入室内。

### 9.4 水与风的可见反馈

水面至少有岸边深浅变化、柔和波纹、入水/出水反馈和水声；实际可游区域和视觉水域一致。暂不做全场景反射和复杂流体模拟。

风要能被看见：草向、叶片、布料、滑翔装备或少量环境粒子共同反馈方向。普通风不持续用大条粒子遮挡画面；主动引风时反馈明显，结束后恢复安静。

### 9.5 美术验收画面

至少输出六个实际运行机位：起点开阔景、角色近景、崖上回望、滑翔俯视、湖边岸线、遗迹/营地。尽量与基线保持相同分辨率、FOV、时间和机位；地形重排导致坐标不能直接对应时，记录相同地标锚点与变换原因。

每个机位检查：轮廓、尺度、颜色统一、阴影与接地、前中远层次、可玩路径可读性、穿模和占位资源。画面不能靠关闭主要对象、修改相机到不可玩角度或用概念图替代来通过。

## 10. M6：风规则、环境互动与基础战斗

### 10.1 风场是一个系统，不是三个互不相关的效果

建立可查询的统一风场，例如 `WindSystem.sample(position, simulationTime)`，返回方向、强度及必要的局部风信息。草木、滑翔和轻物体都读取这个系统；阵风和局部上升气流使用同一时间源和可重现种子。

固定世界风、局部风区与玩家引风分层合成，限制最大强度并平滑进入/退出。渲染噪声可以增加自然感，但不能显示向左吹，实际把玩家推向右。

### 10.2 引风能力的最小完整定义

玩家选择方向后产生有限作用范围和时长的风脉冲，作用于标记为可受风的轻物体、风动机关，以及空中滑翔状态。参数集中配置；冷却、反馈和允许状态明确。

施放前有方向/作用对象反馈，施放时有视觉与声音信号，失败时解释原因。不可对远处不可见物体隔墙生效；超出范围、重量过大或路径受阻时，不发生隐形位移。

轻物体采用同一碰撞与运动规则。落入无法到达位置时有明确重置手段，重置只恢复局部谜题状态，不清空全局进度。

### 10.3 首个机关与两条解法

推荐机关：遗迹入口前有断开的步道和可移动轻型构件，玩家可以使用引风使构件到达明确位置，形成可站立通路；也可先攀到侧面高点，利用可观察的上升气流滑翔到备用入口。

两条解法都要经过正常物理与可达性验证，不是分别触发隐藏传送。机关打开后，在可见结构、声音、交互提示和存档中同步体现。玩家不知道全部规则也能通过观察获得线索。

主动引风不是随时无限向上飞的按钮。控制作用上限、冷却与耗费，避免破坏所有地形挑战；但合理的创造性解法应保留，不能只允许唯一脚本顺序。

### 10.4 玩家战斗

先做一套可靠的轻攻击与闪避，再恢复弓和其他既有武器。每次攻击具有起手、有效窗口、收招；有效窗口结合三维范围、动作朝向、障碍过滤与目标 ID 判定，同一挥击不能连续每帧重复伤害。

命中反馈包括敌人反应、短促音效、适量命中停顿与可关闭/可调的镜头反馈。原有命中停顿可以保留，但不能暂停输入采集造成手感迟滞。

闪避有清楚位移、消耗和无敌窗口，不可无冷却无限连按。攻击和闪避的取消关系明确，不靠意外状态叠加获得无敌。

弓箭必须具有真实可理解的瞄准点、射出位置、飞行与碰撞。默认右键瞄准、左键射击；退出瞄准不是自动放箭。箭数、弓状态、耐久与 UI 同步，不能隔墙命中。手机有对应操作。

### 10.5 敌人

第一种敌人至少具备巡逻、发现、接近、攻击预备、攻击、恢复、受击、失去目标和死亡状态。攻击前给出可见可听的预警；伤害由有效窗口或碰撞事件产生，不是玩家站近后每秒扣血。

敌人不会穿墙直追，不会在高差不合理时隔空近战；受击后有反应，但不必把小怪做成复杂行为树。脱离区域会合理返回，死亡奖励只发一次。

### 10.6 M6 验收

同一风向对草木、角色和物体一致。引风在不同位置遵循相同规则，机关两条路线可完成；物体丢失后可恢复。战斗可通过观察和躲避完成，不靠数值硬换血；墙后、高差、连续点击、死亡重复奖励均有测试。

## 11. M7：引导、界面、声音与手机体验闭环

### 11.1 代表性区域的目标节奏

以下是首次游玩的设计目标，不是实际完成时间承诺，也不要求用强制等待凑分钟数。

| 游玩段落 | 体验内容 | 设计验收 |
|---|---|---|
| 0—1 分钟 | 走出小路，看到风塔和近处小目标 | 不读长篇说明也知道可以探索 |
| 1—3 分钟 | 走到短崖，选择攀爬或绕路，在平台休息 | 路线自由、耐力易懂、失败可恢复 |
| 3—5 分钟 | 在高处观察，自选落点并滑翔 | 登高带来新信息，落点不是强制锁定 |
| 5—8 分钟 | 接近遗迹或绕过营地，尝试风与机关 | 规则一致，玩家可以试错 |
| 8—10 分钟 | 完成挑战，领取奖励并开启捷径 | 奖励有后续意义，世界状态确实改变 |
| 10—15 分钟 | 自愿探索支路，回看已走路线，望见下一地点 | 有继续探索的理由，不是被迫重复操作 |

引导按场景出现：先移动，再观察，再攀爬，再滑翔，再引风。不在标题页一次列出全部系统并要求玩家记住。提示可以重新查看，已经掌握的操作不频繁打断。

### 11.2 默认操作表

操作集中配置，帮助、按键提示和实际输入读取同一份绑定。与旧操作不同之处明确提示。

| 动作 | 电脑默认 | 手机默认 |
|---|---|---|
| 移动 | WASD | 左摇杆 |
| 冲刺 | Shift + 移动 | 明确的摇杆外圈阈值或独立按钮 |
| 观察 | 鼠标 | 右侧固定视角区拖动 |
| 跳跃 | 空格 | 跳跃按钮 |
| 滑翔开合 | 空中再次按空格 | 空中再次点跳跃/滑翔按钮 |
| 进入攀爬 | 面向可攀墙面并按 E | 接近墙面时的攀爬交互 |
| 攀爬松手/地面闪避 | Ctrl，按状态区分 | 对应上下文按钮 |
| 近战 | 非瞄准时左键 | 攻击按钮 |
| 弓箭 | 右键瞄准、左键射击 | 瞄准开关、射击按钮 |
| 主动能力 | F 使用当前能力 | 能力按钮 |
| 能力选择 | 数字键/能力菜单，按解锁情况 | 简洁能力选择面板 |
| 普通交互 | E | 上下文互动按钮 |
| 行囊与地图 | Tab / M | 明确可点击入口 |
| 暂停 | Esc | 暂停按钮 |

E 的优先对象要由距离、视线和上下文确定；同一次按键不得同时开箱和进入攀爬。死亡、菜单、对话不消费世界战斗输入。攀爬输入采用该表默认方案，不混用旧长按空格规则造成意外展开滑翔。

### 11.3 手机交互

左区只移动、右区只转镜头，按区身份绑定，不能按各自区域内部 x 坐标重新推断用途。按钮区域不落入镜头拖动逻辑；使用指针 ID、捕获、取消和捕获丢失处理多指。

至少完成移动+转向+跳跃/攻击的组合测试。按钮建议有效触控面积不小于 48 CSS 像素；此为本项目验收目标。适配安全区、刘海、系统手势区与浏览器工具栏变化。

横屏优先。竖屏显示转横屏提示，必要时暂停世界，但不要因为强制全屏或旋转权限失败而无法进入游戏。回到横屏不重开局、不丢进度。

### 11.4 HUD 与可读性

主要界面保留生命、当前能力、必要时出现的耐力、接近目标时的交互提示。地图、行囊、武器和材料都有入口，但不把整套信息常驻满屏。

保留用户可查看目标的能力，不让任务列表替代环境引导。机关可用、不可用、冷却和失败原因有明确表现，不能只靠颜色区分。中文字体、字号、按钮文案在手机上逐项检查。

增加视角灵敏度、镜头反转、震动/晃动强度、音量和画质设置；设置独立保存，不和一次游戏进度绑定。没有硬件震动能力时不假装已验证触觉反馈。

### 11.5 声音

先审听现有音效，保留合适部分。脚步按地表与落脚相位触发；风声按环境与滑翔强度变化；水边、遗迹、敌人预警、命中和奖励层级清楚。

音乐留白，不持续用高强度音乐覆盖环境信息。音频资源统一响度和循环接缝，限制重复叠音；静音与音量设置有效。只在浏览器允许的用户交互后恢复音频，后台和暂停策略明确。

授权资源与合成音都可以使用，但必须实际听验；不能只因为文件加载成功就标记“音效完成”。

### 11.6 M7 验收

从清空的新版本测试档开始，在不使用作弊状态写入和传送的情况下，完整游玩首个区域。检查引导、两条路线、机关、可选战斗、奖励、存档、死亡和重生。

完成桌面实机与实际可用手机的连续演示。若没有真实手机，移动自动化可以先做，但状态必须写“移动模拟通过、真机待验证”，不能认定手机交付完成。

## 12. M8：把品质覆盖到现有游戏，不停留在样板间

### 12.1 内容盘点与迁移

建立逐项内容清单，按当前 HEAD 记录塔、灵祠、营地、种子、宝箱、篝火、NPC、旧能力和终局。每项标记 `已迁移 / 已验证 / 暂留旧模式 / 阻塞`，并写明依赖。

每完成一组就运行实际路线和存档回归。不要只把旧坐标塞回新地形，也不要把旧世界整体搬到远处但继续更新不可见实体。

### 12.2 三座塔

保留数量，不增加新塔。每座塔的接近路线、轮廓和登顶过程应有区别，例如短崖与平台、湖岸与风道、山脊与避风段。登顶能获得新的视野、检查点或地图信息，不只是改一个布尔值。

塔体碰撞、平台、相机、气候和复活位置一致。初始或适当进度的角色可按设计路线登顶，不能依赖全部隐藏收集或已知漏洞。

### 12.3 四个灵祠与既有能力

先保留已有四术概念与相关进度 ID，再改造判定与关卡表现：爆鸣要有落点、有效范围和障碍处理；霜息要明确合法水面与可站平台；牵引要有目标选择、拿放和碰撞；凝时要有对象、时长、解除与可恢复状态。

每个灵祠至少有“理解规则—一次变化应用—领取奖励”的小过程。能绕行的解法应是有意义的空间选择，不能因为墙没碰撞、祭坛只检查 x/z 或奖励触发缺少条件而无意跳关。

可保留合理多解。教学提示不直接替玩家解谜；失败后可重置局部机关。进入、退出、死亡、重开和读档都不会把室内临时物体泄露到野外。

新引风能力不自动让所有旧谜题失效。逐个验证能力组合；不能用统一禁用所有自由操作来掩盖关卡问题。

### 12.4 营地、收集与经济

三个既有营地复用同一敌人基础和可用美术，但在地形、敌人站位、绕行路径和奖励上区分。敌人不会聚成一团堵住出生点，也不会隔墙攻击。

宝箱开启有可见状态；种子与重要奖励只领取一次。收集物放在值得观察的位置，不平均撒满地图。掉落池超出容量时有明确策略，不能悄悄生成不可见但会阻塞或被拾取的物体。

既有食物、耐久、烹饪功能保留可用接口；首个区域可以减少展示，但整合后对应入口与反馈不能失效。奖励对耐力、补给、装备或捷径有实际意义，避免大量没有用途的货币。

### 12.5 残堡与终局

统一进度规则。新版本默认以“三塔激活且四祠完成”解除残堡封印；NPC、HUD、门的碰撞、Boss 可受伤状态与结局都读取同一规则。若当前产品已有明确不同规则，记录并沿用一致版本，不让剧情说一套、代码做另一套。

Boss 不做大型新系统，先基于统一敌人框架实现两种可辨识攻击、清楚预警和一项后半程变化。攻击、受击、死亡与结局有正常动画/音效/存档，不是一个放大模型贴近定时扣血。

封印未开不能隔墙/远程杀 Boss 提前触发结局；通关奖励不重复发放。通关后可返回探索或重新开始，状态和存档明确。旧档保留旧规则完成记录，不因新版条件变化撤销旧版已通关标记。

### 12.6 M8 验收

完成一条新版本的完整正常主线：新开局→首塔与区域→全部必要进度→残堡→Boss→结局→重新加载。另测旧档恢复与旧版入口。每个地点有验证记录，不允许只测试首个区域就声称全图完成。

## 13. M9：性能、稳定性与正式交付

### 13.1 测量方法

先记录设备、操作系统、浏览器版本、窗口/屏幕尺寸、实际内部渲染分辨率、DPR、画质档、HEAD、场景路径和持续时间，再报告性能。

目标为适配桌面档 60 FPS、适配手机档 30 FPS。这是项目目标，不是当前事实，也不是保证所有设备都达到。必须报告帧时间的 P50/P95/P99、明显卡顿、掉帧比例和资源情况，不能只报瞬时或平均 FPS。

无头浏览器、软件渲染器、模拟器、桌面移动 viewport 和自动化 WebKit 只记相应环境测试；不能把这些结果写成 iPhone Safari 真机性能。测不到的 GPU 时间、显存和温度写“未获取”，不要推算成实测。

### 13.2 优化顺序

先看实际瓶颈，再依次处理过多绘制调用、透明草木过度覆盖、阴影成本、重复材质/几何、每帧对象分配、全局 UI 重渲染、不必要模拟、资源加载峰值和未释放对象。

静态资源复用；植被按区域实例化并做适当裁剪与远近分级；活动物体有容量和回收策略。HUD 选择订阅需要的字段，避免每个模拟步重建全部菜单数据。

至少提供低/中/高或自动画质。手机可降低内部渲染比例、草密度、阴影分辨率和后期，但不能降低碰撞可靠性、改变耐力或让模拟变慢。自动降档要有缓冲，避免分辨率来回跳变。

首屏只加载当前必要资源，其他内容按场景加载；失败有重试或清晰错误，不静默黑屏。资源应本地可发布、缓存策略清楚。只有项目确实有离线缓存时才验收离线，不把已有 PWA 外壳等同于已支持完整离线游戏。

### 13.3 稳定性检查

桌面和可用手机连续游玩至少十分钟，并重复进入/离开灵祠、开关地图/行囊、死亡重生和返回标题。检查对象、事件监听、音频节点和内存趋势，不要求浏览器 GC 后每次回到完全相同数字，但不得持续无界增长。

检查背景恢复、窗口尺寸变化、触控取消、音频恢复、慢速加载、资源失败、存档异常与渲染上下文丢失的合理恢复路径。无法自动恢复时显示可理解提示，并保护存档。

### 13.4 构建、发行包和旧 ZIP

运行实际存在的类型检查、lint、原有测试、新游戏测试、浏览器检查和无迁移副作用的生产编译。原有失败与新引入失败分别列出，但不能把新失败归咎于基线。

原仓库有 `packed/aetherwake.zip` 发行文件。[R11] 源码更新后，必须明确它仍是旧版本，或者在用户允许生成交付包的范围内用可重复流程更新；不要让 README 指向一个与新源码不一致的 ZIP。生成交付包时记录源提交/工作树状态，排除凭据、`node_modules`、缓存和测试隐私数据。

不擅自自动部署。交付本地构建、任务分支和准确的预览方法即可；生产合并或发布另按明确授权执行。

## 14. 建议代码边界：增量整理，不搞一次性大重写

以下是职责划分建议，不是要求机械创建同名空文件。已有合理结构可以沿用；迁移时保留测试并一次只改一个职责。

```text
aetherwake/src/game/
  input/          设备适配、持续输入、命令队列、绑定、重置
  simulation/     固定时钟、世界状态、事件、可重现测试入口
  physics/        碰撞、支撑、运动物体、物理世界唯一驱动
  character/      运动状态机、耐力、控制器、动画和挂点
  camera/         探索/攀爬/滑翔/瞄准与遮挡
  world/          地形数据、区域、地标、生成和加载
  wind/           统一风场、局部风、引风
  combat/         攻击窗口、敌人状态、投射物与反馈
  interaction/    目标选择、机关、能力、局部重置
  progression/    任务条件、奖励、门、检查点和结局
  rendering/      材质、天空、水、植被与画质
  ui/             HUD、地图、行囊、设置与触控
  audio/          音频事件、环境与混音
  persistence/    版本化存档、校验、备份和迁移
```

关键约束：模拟逻辑可以在无 DOM、无 WebGL、无真实音频的测试环境下运行；外部效果通过事件或可替换适配器发出。对象 ID 稳定，场景重置不会复用上一局的全局可变状态。参数与关卡数据集中管理，减少魔法数字。

推荐新增脚本名：`test:game`、`test:game:e2e`、`check:world`、`build:app`。这些是要求执行者接入后提供的命令，不是声称仓库现在已经存在。沿用能支持项目的现有测试工具；确需新增时只增加必要兼容依赖并保留锁文件。
